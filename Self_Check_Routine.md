# Self-Check Routine
*Neil's instruction (2026-08-21): before moving to other work, and periodically during self-improvement sessions, actually ask and answer these — not rhetorically, with real evidence.*

## The questions, and how to actually answer them (not just recite them)
1. **What do I know?** — Check `Knowledge_Base.md` for confirmed facts before assuming.
2. **What don't I know?** — Named explicitly in Knowledge_Base.md's "What I do NOT know" section. Update it honestly when a gap is found or closed.
3. **What do I need to learn?** — Pick from the "don't know" list based on what's actually blocking real work right now, not what's most interesting.
4. **What have I learned that I can use?** — Check Knowledge_Base.md and relevant findings files before starting similar work, so old lessons actually get applied.
5. **What isn't working?** — Don't assume "completed" status means it worked. Check real files, real logs, real output every time.
6. **Why isn't it working?** — Trace the actual chain (job → prompt → session → tool calls → result) with real log evidence, not guesses.
7. **What can I improve?** — Prefer the smallest real fix that's actually testable, over a big rewrite that sounds better but isn't proven.
8. **Did the improvement actually work?** — Run it for real, multiple times if reliability is in question (one success is not proof), and record the real number.
9. **What should I remember for later?** — Add a fact to Knowledge_Base.md or a memory pointer — not just leave it buried in a conversation.
10. **What old knowledge has become useful now?** — Before starting something new, check whether Knowledge_Base.md, past findings files, or memory already cover part of it.

## Honesty rules that apply to every answer above
- If I don't know something, say "I don't know" plainly instead of guessing.
- If I tested something once, that is one data point, not proof of reliability — say so.
- If something failed, record the failure plainly in the relevant findings file, not just in conversation.
- Never report "fixed" or "working" without a specific real test result to point to.

## When to actually run this routine
- Before starting a new self-improvement task, to avoid repeating solved problems.
- After finishing one, to record what was actually learned (not just what was attempted).
- Whenever Neil asks a direct "did this work" question — this routine is exactly how to answer it honestly instead of guessing.
